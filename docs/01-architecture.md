# 1. System architecture

## Overview

```
                    Internet
                       │  80 / 443 only (UFW)
              ┌────────▼────────┐
              │      Caddy      │  TLS termination, security headers, 12 MB upload cap
              └────────┬────────┘
                       │ http://app:3000 (Docker network)
              ┌────────▼────────────────────────────┐
              │  Next.js 16 app (Node 22)           │
              │  ─ Server Components  → reads       │──── dbRead  (role rc_readonly: SELECT only)
              │  ─ Server Actions     → writes      │──── db      (role rc_owner, inside adminMutation)
              │  ─ /api route handlers (files, health)
              └────────┬────────────────────────────┘
                       │
              ┌────────▼────────┐        ┌─────────────────────────┐
              │ PostgreSQL 16   │        │ uploads volume          │
              │ triggers, views,│        │ (bills, receipts)       │
              │ CHECK constraints        └─────────────────────────┘
              └─────────────────┘
       Daily: pg_dump + uploads tar → /opt/.../backups → rclone → off-site storage
```

Everything runs on the single Hostinger KVM 2 VPS with Docker Compose: `postgres`,
`migrate` (one-shot: applies migrations + grants), `app`, `caddy`. No external services.

## Why these choices

| Concern | Choice | Reason |
|---|---|---|
| UI + API | Next.js App Router, Server Components + Server Actions | One codebase; no separate REST layer to secure; data is fetched on the server so the browser never talks to the database. |
| Database | PostgreSQL 16 | Real transactions, `NUMERIC` money, CHECK constraints, triggers, views. |
| ORM | Prisma 6 | Typed queries + versioned SQL migrations. Hand-written SQL migration for triggers/views. |
| Auth | Own implementation: Argon2id + DB sessions | Small, auditable, no third-party service. Sessions can be revoked instantly. |
| Proxy | Caddy | Automatic HTTPS when a domain is added; `tls internal` for IP-only HTTPS. |
| Files | Local volume, random file names, metadata in `Attachment` table | Requirement: local VPS storage. |

## Security layers (defence in depth)

A write is only accepted if **all** of these pass:

1. **Proxy (`src/proxy.ts`)** — requests without a session cookie are redirected to `/login` (convenience gate only).
2. **Session check** — the cookie token is SHA-256 hashed and looked up in `Session`; expired (7 days absolute / 12 h idle) or deactivated users are rejected. Role is read from the DB on every request, so demoting a user takes effect immediately.
3. **`requireAdmin()`** inside every Server Action (`adminMutation()` in `src/lib/mutation.ts`).
4. **Database triggers** — `adminMutation()` runs `set_config('app.user_id', …)` in the transaction. Trigger `app_require_admin()` on every business table rejects the write unless that user exists, is active and is `ADMIN`. So even a bug in application code cannot let a read-only partner write.
5. **Read-only DB role** — every page/report read uses `dbRead`, connected as `rc_readonly`, which has `SELECT` only (and cannot see password hashes or sessions).

Other measures: Argon2id hashing, per-account lockout (5 failures → 15 min) + per-IP rate limit,
generic login errors with timing equalisation, httpOnly/SameSite cookies (`Secure` once HTTPS is on),
Next.js Server Action origin checks (CSRF), security headers, zod validation on every input,
DB CHECK constraints, and an append-only audit log.

## Financial safety

* Financial rows (payments, expenses, receipts, withdrawals, contracts, stock movements) **cannot be deleted** — a trigger blocks `DELETE`. Mistakes are **voided** with a mandatory reason; voided rows are frozen and excluded from every balance.
* `createdById / updatedById / voidedById` are stamped by the database from the acting user — they cannot be forged.
* Every INSERT / UPDATE / VOID / DELETE on business tables is written to `AuditLog` by a trigger with the full before/after row. `AuditLog` rejects UPDATE and DELETE.

## Code layout

```
prisma/
  schema.prisma                 data model
  migrations/…_init             tables (generated by Prisma)
  migrations/…_integrity_…      CHECKs, triggers, audit, ledger views (hand-written SQL)
  sql/grants.sql                read-only role privileges (re-run after each migration)
  seed.ts                       first admin + default categories
src/
  proxy.ts                      cookie gate
  lib/db.ts                     db (writer) + dbRead (read-only) clients
  lib/auth/                     password hashing, sessions, guards, rate limit
  lib/mutation.ts               adminMutation(), error mapping, app-level audit
  lib/queries/                  read models (SQL over the ledger views)
  lib/format.ts                 Rs. / date formatting
  components/ui/                design-system components
  components/layout/            sidebar, top bar
  app/login/                    sign-in
  app/(app)/                    authenticated pages (dashboard, modules, settings)
tests/                          integration tests against a real PostgreSQL test DB
deploy/                         Caddy, Postgres init, backup/restore scripts
docs/                           this documentation
```
